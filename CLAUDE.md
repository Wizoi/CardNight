# CardNight

## Project goal

Build an app to help pick a game for poker night. `games.md` is the group's actively-maintained house-rules doc; `app/` is a first, simple static version of the picker built from it. `table/` is a separate, newer project: an actual playable virtual table (one game at a time, starting with Midnight Baseball) against computer opponents, meant as a local proving ground for game logic before a possible Android port.

## What's in this repo

- **`games.md`** — the reference doc for the poker variants our group plays. This is the source of truth for house rules (including current game count, open questions, and anything else that lives in its own sections there — don't duplicate that data here).
- **`app/`** — a static HTML/CSS/JS picker app, no build step, no server, no dependencies. Open `app/index.html` directly in a browser. See "The app" below.
- **`table/`** — a static HTML/CSS/JS virtual poker table that actually plays hands against AI opponents, with real chip buy-ins/rebuys/cash-outs and day-over-day history. Independent of `app/` — no shared code. See "The table app (`table/`)" below.
- **`personas/`** — expertise/character documents backing the project's direction and the `table/` app's AI opponents. See "Personas (`personas/`)" below.

## How `games.md` is structured

- **Game Categories** section near the top groups all games into five buckets: Guts, Stud-based, Texas Hold'em variant, Baseball, Other. Each game entry also has its own `Category:` field.
- **Index** is an alphabetical list of `[Game](#anchor)` links to each entry's heading below — numbers-first names (3-33, 5.5-21, 7-27) sort before letters.
- **Per-game entries** use consistent field labels where they apply: `Category`, `Family` (for Baseball/Stud-based games, cross-referencing sibling games), `Deal`, `Wildcards`, `Play`/`Betting`, `Winning`/`Goal`, `Tie-breaker`, `Research note`. Not every game has every field — house rules genuinely differ game to game.
- **`(New)` tag** on a game's `Category:` field (and in the Index/Game Categories listing) marks an entry that isn't part of the original house list — a sibling/relative game surfaced during research and documented as a candidate worth trying, not one we've actually played.
- **"House rule" sections** near the bottom consolidate rules that apply across multiple games rather than repeating them in full on every entry: table size, chips & betting defaults, split-pot tie handling, the baseball family's shared wildcard rule, and the stud family's typical deal shape. Individual entries still note briefly how they relate to (or deviate from) these defaults.
- **Research notes** were added to every entry after a 2026-08 web research pass cross-referencing each game against published home-poker rule sites (pagat.com, Wikipedia, pokermike.com, etc.) — informational, not confirmed house rules. They're being reviewed and folded in one game at a time: settled findings move into the entry's actual rule fields, interesting-but-unadopted alternatives become a **Variants:** bullet, and each entry's own **Sources:** bullet holds the links. There's no separate consolidated source list — link at the entry, not at the bottom.
- **No hard player caps.** Table size is 5–8 players; games that would exceed a single 52-card deck at a full table (Deep or Double Screw, Free Enterprise, Mexican Sweat, 3-5-7 Guts) adapt their deal shape to player count rather than capping who can play. See "House rule: table size" and each entry's Deal field.
- The doc previously carried an Open Questions section (rule ambiguities to resolve with the group) and a "Future app fields (draft)" proposed-schema section; both have since been resolved/removed — Open Questions ran dry as each item got settled and folded into its entry, and the future-fields schema was dropped (2026-08-28, user's call) rather than pursued.

## The app (`app/`)

- Plain HTML/CSS/JS, no framework, no build step, no dependencies — `app/index.html` opens directly in a browser (`file://` works fine).
- `app/games-data.js` is a hand-curated structured version of `games.md`, one object per game — `id`, `name`, `category`, `isNew`, `icon` (a unique emoji per game), `players` (`{min, max}`, both fixed at 5–8 with an optional informational `note`), `before` (pre-setup decisions), `setup`, `gameplay`, `win`, `keyDecisions`, `repeats` (things worth repeating mid-game), and `script` (a dealer's read-aloud explanation). **This file is not generated from `games.md` — there's no automated sync. When `games.md` changes, check whether the matching entry here needs updating too.**
- A few games (currently Deep or Double Screw, Mexican Sweat) have a `resolvePlayers(n)` function instead of a static note, so their pre-setup guidance (deal size, passing pattern) adapts live to the "players tonight" count entered in the app header.
- `app/app.js` handles filtering (by category, and an "include New games" toggle), the "Pick for me" random picker, and hash-based routing (`#/game/<id>`) between the grid and per-game detail view. `app/style.css` is the felt-green poker-table look.
- Smoke-tested with a one-off Playwright script (not checked into the repo) that loads `index.html` via `file://`, exercises filters/detail-view/back/pick-for-me, and checks for console errors. No project-level run/test skill exists yet for this app; consider `/run-skill-generator` if that testing flow gets reused.

## The table app (`table/`)

- Plain HTML/CSS/JS, no framework, no build step, no dependencies — `table/index.html` opens directly in a browser (`file://` works fine). Independent of `app/`: no shared *code*, its own `style.css` (reuses `app/style.css`'s felt-green CSS variable palette by value, not by reference). One deliberate exception (2026-08-26): `table/index.html` loads `../app/games-data.js` directly for its `GAMES` array, so the picker screen and the in-game "how to describe it" box can show each game's curated icon/category/dealer-script without duplicating that data — see `gameDataFor` under "The night/meta layer" below.
- **Twenty-seven games supported so far**: Midnight Baseball, Daytime Baseball, Rainy Day Baseball, Free Enterprise, Follow the Queen, Seven and What Makes It, The Good the Bad and the Ugly, Mexican Sweat, Cincinnati, Criss Cross, Deep or Double Screw, 3 Buy 5 / 5 Buy 5, Four-Two-Two, 3-5-7 Guts, Wild in Your Hand, Omaha, Seattle, Boise, Jersey Hold'em, 5.5-21, 7-27, 3-33, Acey Ducey, Blind Man's Bluff, Game of Life, Pair of Jacks Trips to Win, and Anaconda (Pass the Trash) — plus a "night" meta-layer (cut-for-deal, a rotating game-picker) that lets a sitting span more than one game. Built as a **pluggable game-family architecture** rather than one hardwired game — every game documented in `games.md` is now built; see "Adding more games (backlog)" below, which is now empty.
- `table/js/` is split so the game-logic core (no DOM) stays separable from the UI, since that core is the part most worth porting to a future Android app. Shared foundation, reused by every game:
  - `deck.js`, `hand-evaluator.js` (5-card poker hand ranking, including wildcards and Five of a Kind, plus `describe()` for a rank-specific label like "Three of a Kind (Js)"; `bestHand(cards)` already picks the best 5 from any pool size ≥5, which is what stud/community games need — pure card/hand primitives). `deck.js`'s `drawWithReshuffle(pile)` takes any `{deck, discardPile}`-shaped object and reshuffles the discard pile back in once the deck runs dry — used both by Midnight Baseball's 4-bonus draw and by the stud engine's normal per-street dealing (a full table's ordinary dealing alone can use most of a 52-card deck, so even a couple of 4-bonus buys before anyone's folded can run it dry mid-street, not just on a bonus draw — a real bug caught by stress-testing before it shipped). `hand-evaluator.js`'s `bestHandWithSumWild(cards, targetSum, rankValue)` (Seven and What Makes It) tries every subset of a hand as a candidate wildcard set, keeping only those that partition into disjoint groups summing to `targetSum` — but only actually *scores* the maximal valid subsets (no other valid subset is a strict superset), not all of them: a strict superset that's still valid always weakly dominates a smaller one, since a wild card can always fall back to its own real identity in `bestHand`'s resolution search, so scoring the non-maximal candidates too would be redundant. Skipping that pruning step was a real, caught-before-shipping performance bug — scoring every valid subset instead of just the maximal ones was ~700x slower (87ms → under 0.2ms per call) with no difference in the result. `bestLow(candidateFiveCardHands)` (hold'em's optional hi-lo split) evaluates ace-to-eight low hands — exactly 5 unpaired cards each ranked 8-or-under, aces low, no wildcard support at all (no hold'em variant here has a fixed wildcard rule, so the extra complexity of an assignable-to-any-low-rank wild card wasn't needed). It doesn't know about hole/board cards — callers (`rules-holdem.js`) generate whichever 5-card combos their hand/board split rule allows and hand them over as a flat array to score.
  - `chip-economy.js` — pure wallet math (buy-in/rebuy/cash-out/net); no betting-round logic lives here.
  - `betting-engine.js` — generic ante-collection and call/raise/fold chip accounting (`startRound`/`getCurrentBettor`/`submitBet`/`maxRaiseDollars`/`collectAntes`), extracted out of what used to be entangled inside `rules-midnight-baseball.js`. Has no concept of a "board to beat" or what a fold/win means for a given game — every rule engine wraps it with same-signature functions that add their own win-detection/logging on top, so this extraction was a pure refactor (verified against the Node regression suite for zero behavior change before anything else was built on top of it). `round.allIn` tracks anyone who's called or raised for less than the current bet (an all-in-short) — **a real, previously-latent bug** across every family that uses this module: without it, `getCurrentBettor`'s "has this player matched the current bet" check is permanently false for an all-in-short player, so once someone else raises again, they get handed the turn forever with no chips left to ever actually match it. Single-game testing never surfaced it (going exactly broke mid-raise, rather than merely low on funds, is rare within one game); a Playwright multi-game-night pass caught it directly, by sending a human busted out of Omaha's blinds into a second game (Cincinnati) and watching its betting round hang indefinitely. Fixed at the source (`getCurrentBettor` now also skips anyone in `allIn`) rather than patched per-game, so every family that reuses this module — stud, community stud, Mexican Sweat, hold'em — got the fix at once; `rules-holdem.js`'s `postBlinds` (which builds its first betting round by hand rather than via `startRound`, to seed it with posted blinds) needed the same `allIn` set threaded through by hand too. `maxRaiseDollars` also takes an optional `walletChips` bound (default `Infinity`, so a caller that omits it behaves as before) — added when a full games.md audit (see below) traced hold'em's "$0.00 raise" log oddity back to this function never checking affordability at all, only the configured cap; every other family's low $2 cap always happened to bind first, which is why this was latent everywhere but only visibly broke hold'em's genuinely uncapped betting.
  - `baseball-family-wildcards.js` — the shared 3s/9s-bought-wild + 4-bonus-buy mechanic (`games.md`'s "House rule: the baseball family"), used by all three baseball games. Takes the specific card/hand reference rather than searching a hand by predicate, since a single-reveal game (Midnight Baseball) can safely assume only one live unresolved 3/9 at a time, but a multi-street stud engine can't.
  - `ai-profiles.js` — three deterministic AI awareness profiles (Cautious / Balanced / Aggressive) sharing one heuristic; not random. Decisions are judged only from what's actually face-up plus how many unknowns are left — never from the AI's own hidden cards. `worthPursuing`/`decideBuy3`/`decideBuy9`/`decideBuy4` are engine-agnostic (they never reference Midnight Baseball directly) and are reused as-is by the stud engine; only `decideBet`/`decideContinue`/`worthRaisingAsLeader` are MB-specific since they read its "beat the board" state shape directly.
  - `game-registry.js` — the map of every playable game (`midnightBaseball`/`daytimeBaseball`/`rainyDayBaseball`/`freeEnterprise`/`followTheQueen`/`sevenAndWhatMakesIt`/`goodBadUgly`/`mexicanSweat`/`cincinnati`/`crissCross`/`deepOrDoubleScrew`/`threeBuyFive`/`fourTwoTwo`/`threeFiveSeven`/`omaha`/`seattle`/`boise`/`jerseyHoldem`), each entry naming its `uiFamily` (which `table-ui-*.js` renders it) and a `createOrchestrator` factory. This is the seam new games hang off of.

  - `rules-midnight-baseball.js` — deal, turn/reveal mechanics, wildcard buys, win detection, now delegating betting-round math to `betting-engine.js` and the 3/9/4 buy mechanic to `baseball-family-wildcards.js`. A player leaves the hand only by declining a mandatory 3, running fully out of cards without beating the board, or folding at any time. `currentTurnPlayerId` is a **pure read**, safe to call constantly from rendering. - **Stud family** (dealer-dealt cards on a fixed per-game schedule, a betting round after each street — the structural opposite of Midnight Baseball's player-paced reveal). Six games live here so far: Daytime Baseball, Rainy Day Baseball, Free Enterprise, Follow the Queen, Seven and What Makes It, The Good the Bad and the Ugly.

    - **Free Enterprise's `enterprisePile: {priceScheduleDollars, finalRoundMultiplier}`** (rebuilt 2026-08-25 after the user corrected a wrong initial implementation — see below): a shared 3-card face-up spread (`state.enterprisePile`), dealt from the top of the deck and topped back up to 3 the instant any card leaves it. Every card after the initial 2 down comes from a turn at this pile rather than a normal per-player deal, so `dealNextCard` returns `needsDecision: "enterprisePile"` for every remaining street instead of dealing a card outright. On their turn a player does exactly one of: **buy** a pile position (`resolveEnterpriseBuy`, priced by position via `currentEnterprisePriceDollars` — $1/$2/$3, doubled on the final street — stays face up since the table already saw it); **wipe** the pile (`resolveEnterpriseWipe` — free, discards all 3 and deals a fresh 3, but doesn't end the turn — it re-arms the decision as `"enterprisePileAfterWipe"`, buy-or-free only, no second wipe); or take a **free** card off the top of the deck (`resolveEnterpriseFree`, dealt face down, skips the pile entirely). Face-up/face-down status is therefore determined by *how a card was acquired*, not by a fixed street schedule — a genuinely new pattern for this codebase (every other stud game's face is fixed per-street in `gameConfig.streets`). A game only ever configures `wildcards` or `enterprisePile`, never both, so `needsDecision` never has to arbitrate between them.

- **Mexican Sweat** — "all down, no looking at your hand": every player's full hand is dealt face-down up front, then each round everyone flips one of their own remaining cards simultaneously and blind (nobody, human included, chooses which card — a player can't see their own hand any better than an opponent watching would, so reveal order is always the dealt order), followed by a betting round. Genuinely different from both other families (no dealer-deals-a-new-card-each-round like stud, no player-paced choice-of-which-card like Midnight Baseball's self-reveal), so it gets its own small engine rather than a config on either existing one.

### Testing (`table/tests/`)

A committed, plain-Node regression suite — `node table/tests/run-all.js` runs everything with zero dependencies and no build step, matching the rest of this project's conventions. Added 2026-11-20, prompted by a user question about what mobile-app-porting work this project could do now, structurally, to preserve its current "game rules are testable without a browser or emulator" property before any actual Android/iOS work starts — this is purely that structural groundwork; no platform/native work has happened yet.

- **`harness.js`** / **`check.js`** — the shared `vm`-sandbox file loader and pass/fail assertion helper every ad hoc scratchpad regression test in this project's history had hand-rolled from scratch, written once. `harness.js`'s `load(files, names, extraSandbox)` loads a list of `table/js/*.js` files into one Node `vm` context in `<script>`-tag order and hands back the requested top-level globals; `check.js`'s `makeChecker()` gives `check(desc, cond)` plus a `summary()` that both prints and returns a failure count, so `run-all.js` can aggregate across files.
- **Why this matters beyond just test hygiene**: `rules-*.js`/`session-*.js`/`ai-*.js` are pure JS with zero DOM or platform dependency (no `document`, `window.*`, `localStorage`, nothing a native WebView plugin would provide) — that's the entire reason this suite runs under plain Node with no browser and no emulator at all. **`layer-boundary.test.js`** makes that property an enforced, repeatable check instead of a one-off manual grep: it reads every `rules-*.js`/`session-*.js`/`ai-*.js` file (comments stripped first, so prose mentioning "the localStorage round-trip" doesn't false-positive), and fails if one of them starts actually calling `localStorage.*`/`document.*`/`window.*`/`Capacitor`/`navigator.*`. Holding this boundary means a future Capacitor-based native port (the one explicitly anticipated by this app's own stated goal, see the top of this file) would only ever need real device/emulator testing for the native shell and UI layer — never for "does this game's rules work," which is exactly the ratio that exists today. `localStorage` itself is already cleanly isolated one layer up, in `history-store.js`/`table-night.js`/`table-fx.js`/`table-ui.js` — confirmed directly (not assumed) before writing this check, and none of those files are scanned by it.
- **Converted test files** (`rules-guts.test.js`, `rules-333.test.js`, `rules-mexican-sweat.test.js`, `rules-draw-poker.test.js`, `rules-anaconda.test.js`, `rules-press-your-luck.test.js`, `table-night.test.js`) — real, previously-reported bugs from this project's own history re-derived into permanent regression coverage instead of disposable scratchpad scripts: the Guts family's showdown-hand-description fix, the dummy-hand-doesn't-auto-win-a-lone-stayer rule, 3-33's per-winner split-payout math, Mexican Sweat's kill-card-not-wildcard mechanic, Draw Poker's Trips-or-better-vs-fold-out distinction, Anaconda's hi-lo description fields, 7-27's buy-back per-turn chain cap plus the flex-ten-still-offered fix, and `table-night.js`'s cross-game status/hand reset. New bug fixes going forward should add a test here (see `README.md`'s "Adding a new test") instead of a throwaway scratchpad script, so the fix stays locked in.

Those were discussed (see the mobile-app-analysis conversation this entry came out of) as the next real steps if/when an actual port starts, but this pass was scoped to the test-structure groundwork only, per the user's explicit ask to make no functional/platform changes yet.

## Working process for the Android port (stages, context reset, handoff)

Added 2026-11-20, once the Android build roadmap existed (a published doc, not yet linked here by URL since it's a Claude Docs artifact rather than a repo file — ask the user for it if a future session needs it) and the user asked for a repeatable handoff method between stages of that work. This is a deliberately right-sized port of a process already proven on three other, larger projects on this machine — `TagPup` (`docs/RETRO.md`), `SmugView`, and `AegidaSafe` (whose own CLAUDE.md says outright: "every rule here comes from a lesson in SmugView or TagPup"). Those three commit their process docs to git; **this project keeps CLAUDE.md itself untracked (`.gitignore`), so the same choice is made here by default for anything process-related below** — local-only, not pushed. Flag if that should actually be tracked like the other three.

**Stages, not phases-with-owners.** TagPup/Aegida's version assumes a team of agents and domain owners; CardNight is one person. Each roadmap step (or small cluster of them) from the Android doc is a "stage." A stage ends with: the actual change committed/pushed (or explicitly not, if it's research/planning only), a one-paragraph note of what was learned or cost time, and this file updated if a rule actually changed. Then `/clear`.

**Context reset mechanics**: `/clear` at a stage boundary, same as TagPup — a retro (or even just a normal next stage) must not run on the long context of the work it's judging/continuing. What carries the state across the reset, same role as TagPup's "memory handoff": Claude Code's own cross-session memory files (not a repo file) — write to memory, before clearing, whatever the next stage genuinely needs that isn't already sitting in a committed file (CLAUDE.md, the Android doc, `table/tests/`). Don't duplicate what's already durable elsewhere; memory is for the connecting tissue (why a stage ended where it did, what's queued next, anything the user said that doesn't belong in a code comment).

**A lightweight retro at each stage end**, scaled down from TagPup's 5-phase/60-minute process to a few minutes:
1. What actually happened (one paragraph, from the real record — git log, this session's own tool output — not recalled from memory).
2. The one thing that cost the most time or nearly went wrong, and the cheaper path, if there was one knowable at the time (TagPup's "blameless" framing: the cause is a missing rule/check, never "the model/the person should have known").
3. At most one instruction change as a result — added here, or better, turned into one of `table/tests/`'s checks if it's the kind of thing a test can catch. TagPup's own hard-won rule applies directly: **a retro that adds rules should remove at least as many** — if CLAUDE.md starts ballooning from this process the same way it has from game-by-game history, that's worth a dedicated trim pass, not more additions.
4. What to carry to the next stage — written to memory, not left to "the conversation will remember."

**Findings, informally**: this project already has an equivalent of the other projects' `docs/findings.md` — the "Known open items (not yet started)" section at the end of this file. Keep using that; no need for a separate ledger at this project's current scale. A real `docs/findings.md`-style file is worth introducing only if the Android work starts generating enough concurrent open issues that a single bulleted section stops being enough to track them.

**Android-specific operational lessons worth having before any native work starts** (ported now from SmugView/Aegida so they aren't re-learned the hard way once the roadmap reaches the Bubblewrap/Gradle steps):
- Gradle needs the Android Studio JBR (`JAVA_HOME` pointed at it), and a Gradle exit code of 0 has been seen on a failed/colliding build — check for the literal string `BUILD SUCCESSFUL` in the output, never trust a piped command's exit code (the pipe reports the pipe's own exit code, not Gradle's).
- Delete old test-result XML before a run; a failed build can leave the previous run's results sitting there, reading as a false "all passed."
- Play Store: `targetSdk` has to stay within about a year of the latest Android release, and **a rejected upload still burns its versionCode** — budget version codes with that in mind, don't treat a rejected upload as a free retry.
- Every fix gets a test that fails against the old code first (already this project's own practice all session, via `table/tests/` and the Node regression scripts before that — nothing new to adopt here, just confirming the instinct transfers).
- Check a premise against real data before writing a fix — the equivalent for CardNight of "curl the real API first": drive the real browser/app state (as this session already does via the Chrome tool) rather than fixing from an assumption about what the code does.
- Ask before a one-way or meaning-changing choice — a storage-format change, a new default a player never chose, anything that would need a migration once real installs exist. Not urgent pre-launch, but worth remembering once there's a live user base that can't just be reset.
- A symptom seen live (on a device/emulator, or in a real browser pass) is a finding recorded in the moment, never deferred to "I'll remember to check that later."
