# ios/ -- the Capacitor-wrapped iOS app (Android roadmap step 11)

Scaffolded 2026-11-25 via `npx cap add ios` after adding `@capacitor/ios`
to `package.json`. Picked up the existing `com.luckofthedeal.app` appId
from `capacitor.config.json` automatically -- no manual rename needed, and
it matches the Android `applicationId` exactly (same convention as every
other app on this account).

## How the source stays untouched -- same design as `android/`

Identical pipeline to the Android side: `table/` itself is completely
unmodified, `tools/build-table.js` builds `table/dist/`, and
`npx cap sync ios` copies that bundled output into
`ios/App/App/public/`. `npm run sync` (root `package.json`) should be
extended to also run `cap sync ios` once the iOS side is actually in
active use, the same way it already runs `cap sync android`.

## Swift Package Manager, not CocoaPods

Capacitor 8's iOS template uses SPM (`ios/App/CapApp-SPM/`,
`Package.swift`) for its own plugins -- no `Podfile`/`Pods/` to manage at
all. This matters for CI: no CocoaPods install step is needed, just
`xcodebuild -resolvePackageDependencies` (or letting `archive`/`-list`
resolve it inline, which they do automatically).

## No committed `.xcscheme` file, and that's fine

`cap add ios` doesn't generate a shared scheme file under
`xcschemes/` -- confirmed directly (not assumed) via a real macOS GitHub
Actions runner: `xcodebuild -list -project ios/App/App.xcodeproj` still
correctly reports the `App` scheme without one, so `-scheme App` works in
CI as-is. No scheme file needed to be hand-authored.

## `ios/App/App/public` and `config.xml` are gitignored -- CI must sync first

Same convention as `android/`'s own `app/src/main/assets/public`: Capacitor's
own `ios/.gitignore` excludes `App/App/public` (synced web assets) and
`App/App/capacitor.config.json`/`config.xml` (generated by `cap sync`).
**A CI job that runs `xcodebuild archive` without first running
`node tools/build-table.js && npx cap sync ios` will "succeed" at a
surface level but silently produce a broken archive** -- confirmed by a
real diagnostic run: `error: lstat(.../App/public): No such file or
directory` appeared mid-build, and because the archive command was piped
through `tee` without `set -o pipefail`, the step reported `success`
based on `tee`'s own exit code rather than `xcodebuild`'s -- the exact
"don't trust a piped exit code" class of bug this project's Android
lessons already warn about, now confirmed to apply here too. Fixed in the
diagnostic workflow by adding `set -o pipefail` and an explicit
post-archive check that the app bundle's `public/` directory actually
exists and is non-empty.

## Pipeline plan, modeled on SmugView's proven `ios-testflight.yml`

SmugView (a sibling KMP project, already published to the App Store) was
surveyed in detail for its actual working iOS CI pipeline. Its
signing/export/upload mechanics are **fully generic** -- nothing
KMP-specific about them -- so CardNight's own pipeline will mirror them
closely:

1. **Archive unsigned**: `xcodebuild archive ... CODE_SIGNING_ALLOWED=NO
   CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY=""`. SmugView's own
   hard-won lesson: archiving WITH signing makes Xcode look for a
   Development profile, which needs a registered test device -- archiving
   unsigned sidesteps that entirely; only the export step actually signs.
2. **Export a signed IPA** via an `ExportOptions.plist` (method
   `app-store-connect`, `signingStyle: automatic`) plus
   `xcodebuild -exportArchive -allowProvisioningUpdates
   -authenticationKeyPath/-authenticationKeyID/-authenticationKeyIssuerID`
   -- Apple's cloud-managed signing handles the Distribution certificate
   server-side, no certificates or provisioning profiles stored in this
   repo or in secrets at all.
3. **Upload via `xcrun altool --upload-app`**, with the output explicitly
   grepped for the literal string `"UPLOAD FAILED"` -- SmugView's own
   caught-live lesson: altool can print that failure while the step/job
   still exits 0.
4. **Pin a specific Xcode version** (`xcode-select -s
   /Applications/Xcode_26.2.app`) rather than trusting the runner's
   default -- confirmed this runner image (`macos-15`) has Xcode 26.0
   through 26.3 available alongside several 16.x versions; Apple currently
   requires Xcode 26+ for new uploads.
5. **Build number = `github.run_number` (+ an offset input to manually
   bump past a reset)**, **marketing version = a workflow input** (e.g.
   `"0.1"`, matching the Android `versionName`) -- both injected via
   `xcodebuild archive`'s own `CURRENT_PROJECT_VERSION`/`MARKETING_VERSION`
   command-line overrides, no need to hand-edit the `.pbxproj` per release.
6. **Secrets**: `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8` (the `.p8` as
   base64 text, decoded in CI under `umask 077`, deleted in an
   `if: always()` cleanup step). SmugView's key is a **Team Key**
   (account-wide, not scoped to one app) -- if the same Apple Developer
   account is used, this may mean reusing the existing key's three values
   as new secrets on *this* repo rather than generating a fresh key.
7. A protected `testflight` GitHub Environment with a required reviewer,
   so the pipeline is `workflow_dispatch`-only and pauses for a human
   approval before spending macOS CI minutes or uploading anything.
